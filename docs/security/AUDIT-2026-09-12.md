# Audit de sécurité — Les Chanvriers Bretons

Date : 12 septembre 2026. Code examiné : espace de travail `C:\lesiteinternetquitue`, incluant les modifications locales présentes au début de l'audit. Domaine observé : `https://www.leschanvriersbretons.com`.

## Résultat : 58/100 — corrections prioritaires nécessaires

Le site dispose de protections réelles, mais un défaut important court-circuite l'authentification administrateur renforcée. Deux API de compte créent un jeton administrateur sur la seule base d'une session client appartenant à une adresse autorisée, sans exiger le mot de passe administrateur ni le TOTP. Ce comportement a été reproduit localement avec les véritables fonctions de signature et de vérification des jetons.

La revue des migrations révèle aussi des politiques SQL permettant potentiellement de modifier les points de fidélité de son propre profil et de publier directement un commentaire approuvé. Leur exploitation en production dépend des privilèges et éventuels correctifs réellement appliqués dans Supabase, qui n'ont pas été consultés.

**La note porte sur la sécurité observable et la solidité des contrôles examinés. Elle est provisoire, ne mesure pas une probabilité de piratage et ne vaut pas certification.** Aucun accès administrateur frauduleux, aucune fuite de données clients et aucune falsification de paiement n'ont été démontrés en production.

## Périmètre et méthode

- Inventaire des **142 fichiers de routes API**, dont **70 routes administrateur**, et des **206 migrations SQL**. L'inventaire exhaustif des fichiers ne signifie pas que chaque branche métier ou chaque instruction SQL a été prouvée sûre.
- Revue ciblée : authentification client/admin, récupération de mot de passe, sessions, middleware, droits sur commandes/factures, paiement Viva, stockage, API publiques, jeu, newsletter, profil et modération.
- Exécution de toute la suite Vitest configurée ; ajout d'une suite isolée de reproductions de sécurité ; contrôle TypeScript et lint du code source.
- Consultation actuelle des avis npm, séparément pour toutes les dépendances et pour la production.
- Dix requêtes HTTP GET de lecture seule sur le domaine : huit sondes initiales et deux vérifications HTML complémentaires. Aucun envoi d'email, achat, création de compte, modification de base ou test de charge en production.
- Recherche de motifs de secrets dans les fichiers texte suivis par Git, sans afficher leurs valeurs. Vérification de présence de paramètres locaux, sans exporter les secrets.

Les recommandations de sécurité et de CSP de la version installée de Next.js ont été lues dans `node_modules/next/dist/docs/01-app/02-guides/`. Le code applicatif et les dépendances n'ont pas été corrigés pendant cet audit ; seuls les livrables et outils de diagnostic ont été ajoutés.

## Constats et corrections

### S01 — Élevée : le contrôle administrateur renforcé peut être contourné

**Statut : confirmé par exécution locale ; identité Supabase simulée.**

Références : `src/app/api/account/login/route.ts:129`, `src/app/api/account/me/route.ts:50`, `src/app/api/admin/login/route.ts`, `src/lib/admin-guard.ts:13`.

La connexion administrateur dédiée vérifie la session client autorisée, le mot de passe administrateur et, s'il est configuré, le TOTP. Pourtant, la connexion client et le GET `/api/account/me` émettent eux aussi un `lcb_admin_session` dès que l'email du client est autorisé. Le garde des API admin accepte ensuite ce jeton sans preuve de passage par le contrôle renforcé.

**Scénario :** une personne possède le mot de passe client ou une session client compromise du compte autorisé. Elle utilise l'API client pour obtenir un jeton admin valide sans connaître le second mot de passe ni le TOTP. Un client ordinaire ne peut pas devenir administrateur par cette voie : le contrôle négatif le confirme.

**Preuve :** deux tests obtiennent un jeton validé par `verifyAdminSessionToken`, même avec un secret TOTP synthétique configuré. Aucune connexion réelle n'a été tentée.

**Correction prioritaire :** retirer l'émission automatique des deux API client. Réserver la création d'une session privilégiée à une authentification renforcée explicite, enregistrer l'identité et le niveau de vérification dans la session. Vérifier qu'une consultation du profil ne renouvelle plus les droits admin. Le TOTP est absent du fichier local examiné ; l'état de production reste inconnu, et l'activer seul ne corrigerait pas le contournement.

### S10 — Élevée, conditionnelle : les points de fidélité ne sont pas protégés par la politique de profil

**Statut : faiblesse confirmée dans les migrations ; exploitabilité sur la base déployée non testée.**

Références : `supabase/migrations/20260215_0001_init.sql:187` et `:290`, `supabase/migrations/20260302001200_loyalty_pack_purchase.sql:4`, `supabase/migrations/20260726000100_kq_support_boosters_points_shop.sql`.

`profiles_user_update_own` autorise la modification de sa propre ligne. Cette ligne contient aussi `loyalty_points`, puis `loyalty_points_spent`. Aucun retrait de droits UPDATE sur ces colonnes ni déclencheur de protection de ces champs n'a été trouvé dans les migrations examinées. Le filtrage correct des champs dans l'API Next.js ne protège pas un accès direct à la Data API Supabase.

**Condition d'exploitation :** le rôle `authenticated` doit disposer du droit UPDATE effectif sur ces colonnes, la table doit être exposée et aucune protection supplémentaire ne doit exister dans la base réelle.

**Impact possible :** gonfler les points ou remettre les points dépensés à zéro, puis obtenir des avantages et achats en points indus.

**Correction :** retirer le droit UPDATE global au rôle client et accorder uniquement les colonnes de profil éditables, ou réserver toutes les écritures à une API/RPC contrôlée. Conserver les soldes dans une table inaccessible en écriture client. Une permission de table globale l'emporte sur une tentative de restriction simplement ajoutée colonne par colonne : vérifier les deux niveaux.

### S11 — Modérée, conditionnelle : modération et champs internes du blog insuffisamment isolés

**Statut : confirmé dans les politiques déclarées ; accès direct en production non testé.**

Référence : `supabase/migrations/20260305100000_blog_comments_ratings.sql:3`, `:39`, `:52`, `:77`.

La politique INSERT des commentaires vérifie le propriétaire et la longueur du contenu, mais pas `status = 'pending'`. Un défaut SQL `DEFAULT 'pending'` n'empêche pas un client de fournir explicitement `approved`. Si INSERT est accordé, l'API directe permettrait donc de contourner la modération et les limites de l'API Next.js.

La lecture publique des commentaires approuvés ne limite pas les colonnes : selon les droits SELECT, `admin_note`, `reviewed_by` et l'identifiant client peuvent être visibles. Les notes du blog ont aussi une politique SELECT publique `USING (true)` portant sur des lignes avec `customer_id`. Cela peut exposer les votes individuels, et pas seulement une moyenne. Aucun contenu privé n'a été collecté pour vérifier cette hypothèse.

**Correction :** imposer le statut et les champs de modération côté SQL, ou supprimer INSERT direct au rôle client. Exposer une vue publique avec les seuls champs utiles et des notes agrégées. Tester les droits avec les rôles `anon` et `authenticated`, pas avec `service_role`.

### S02 — Modérée : un jeton administrateur copié reste utilisable après déconnexion

**Statut : confirmé par exécution locale.**

Références : `src/lib/admin-auth.ts:2`, `:7`, `:121`, `src/app/api/admin/logout/route.ts`, `src/lib/admin-guard.ts`.

Le jeton signé contient une expiration et un nonce, mais aucun identifiant de session révocable. La déconnexion efface le cookie du navigateur uniquement. Un exemplaire copié reste valide jusqu'à son expiration, jusqu'à quatre heures. Le garde ne revérifie pas la session Supabase ni l'appartenance actuelle à la liste admin.

**Impact :** la déconnexion ne permet pas d'arrêter une session volée. La révocation du compte client ne suffit pas à invalider immédiatement le jeton admin autonome.

**Correction :** stocker un identifiant de session ou une version révocable côté serveur, y lier l'identité admin, révoquer à la déconnexion et lors des opérations de récupération de compte. Ajouter un test « jeton copié refusé après révocation ». La rotation de clé est une mesure globale possible en incident, à coordonner avec le redéploiement et le cache de clé.

### S03 — Modérée : limite de taille contournable lorsque `Content-Length` manque

**Statut : confirmé sur le garde applicatif ; déni de service réel non tenté.**

Référence : `src/lib/body-size-guard.ts:11`. Exemples d'appel : connexion et newsletter ; plusieurs autres routes lisent directement `request.json()` ou `request.formData()`.

Le garde annonce 64 Kio, mais accepte une requête sans longueur déclarée ou avec une longueur non numérique. Un corps de 70 Kio sans cet en-tête passe le contrôle dans le test. La lecture JSON intervient ensuite entièrement en mémoire, parfois avant la limitation des requêtes. Le webhook contrôle aussi la taille après lecture : cela refuse le traitement mais ne borne pas l'allocation initiale.

**Limite de la preuve :** le frontal Vercel peut imposer sa propre borne et normaliser les en-têtes. Le test prouve l'insuffisance de la borne applicative, pas une capacité à saturer la production.

**Correction :** lire le flux avec comptage des octets et interruption au seuil, limiter aussi au frontal, vérifier le type de contenu, traiter les erreurs JSON et limiter les uploads avant leur chargement complet. Les limites métier après parsing restent nécessaires.

### S04 — Modérée : redirection externe depuis la vérification d'âge

**Statut : confirmé par exécution du middleware local.**

Référence : `middleware.ts:159` et `:230` ; helper plus robuste déjà disponible : `src/lib/safe-next-path.ts`.

Le filtre local refuse `//` mais accepte une valeur commençant par slash puis antislash. L'analyseur URL la normalise en destination externe. Avec un cookie d'âge valide, le test produit une redirection vers `https://audit-redirect.example/path` à partir du paramètre `next`.

**Impact :** lien d'hameçonnage utilisant le domaine légitime comme point de départ. Ce n'est pas une preuve de vol automatique de session.

**Correction :** employer le helper partagé rejetant les antislashs et caractères de contrôle, puis vérifier que l'origine de l'URL résolue correspond à celle du site. Tester les valeurs encodées et doublement encodées.

### S05 — Modérée, conditionnelle : contrôle d'origine absent sur l'arène et le blog

**Statut : omission et passage du middleware confirmés ; attaque CSRF complète non réalisée.**

Références : `middleware.ts:142`, `src/app/api/arena/rewards/dice/route.ts`, `src/app/api/arena/placard/market/route.ts`, `src/app/api/blog/comments/route.ts`.

La liste des API avec contrôle d'origine ne contient ni `/api/arena` ni `/api/blog`. Un POST avec une origine tierce passe le middleware sur l'arène. Certaines mutations n'exigent aucun corps, comme le lancer collectif. D'autres utilisent `request.json()` sans exiger le type `application/json`.

**Conditions :** une session valide doit être transmise par le navigateur. SameSite réduit fortement les attaques depuis un site distinct, mais ne remplace pas le contrôle d'origine, notamment avec un sous-domaine non fiable appartenant au même site. Le test local ne démontre pas qu'un navigateur transmettrait les cookies depuis n'importe quel domaine tiers.

**Correction :** couvrir toutes les mutations authentifiées, comparer l'origine complète avec une origine configurée, employer Fetch Metadata et/ou un jeton CSRF lorsque pertinent. Garder l'exception webhook explicite. Le contrôle existant compare seulement les hôtes, sans comparer le protocole.

### S06 — Modérée, conditionnelle : limitation dépendante des en-têtes IP et repli permissif

**Statut : comportement local confirmé ; possibilité d'usurpation de l'IP au frontal non démontrée.**

Références : `src/lib/security-rate-limit.ts:33`, `:103`, `:142`, `:153`.

Trois points : la première IP syntaxiquement valide de `X-Forwarded-For` est utilisée sans établir la chaîne de confiance ; une réponse RPC vide autorise la requête ; si la RPC est absente, le repli est une Map locale à chaque instance, sans purge des clés inutilisées.

La production observée est servie par Vercel. Si ce frontal réécrit correctement l'en-tête, l'usurpation directe n'est pas démontrée. Le problème devient concret sur un frontal qui conserve une première IP fournie par le client. Le repli local ne protège pas uniformément plusieurs instances.

**Correction :** utiliser l'identité réseau garantie par l'hébergeur, refuser les réponses RPC incohérentes sur les actions sensibles, conserver un compteur partagé et borner/purger tout cache local. Distinguer compteurs par compte et par IP.

### S07 — Modérée : la newsletter permet de renouveler le quota en changeant d'adresse

**Statut : confirmé par lecture du flux ; aucun email envoyé.**

Référence : `src/app/api/newsletter/subscribe/route.ts:29` et `:59`.

La clé unique combine IP et email. Changer d'email crée un nouveau quota depuis la même IP. De plus, une demande pour une adresse déjà abonnée déclenche à nouveau l'envoi de confirmation. Cela permet un abus de la capacité d'envoi et potentiellement une nuisance envers des destinataires. La réponse `alreadySubscribed` renseigne également sur l'état d'inscription d'une adresse.

**Correction :** imposer séparément une limite par IP, par destinataire et globale, ajouter un délai d'envoi par destinataire, ne pas renvoyer un email à chaque requête répétée, rendre la réponse publique neutre. Si nécessaire, vérifier le contrôle de l'adresse avant activation définitive.

### S09 — Modérée selon l'avis fournisseur : dépendance de développement vulnérable

**Statut : confirmé par npm audit et le fichier de verrouillage.**

`@humanfs/node` **0.16.7**, dépendance de développement, est affecté par [GHSA-p498-v437-472g](https://github.com/advisories/GHSA-p498-v437-472g). La correction est disponible à partir de **0.16.8**. L'avis concerne la copie de fichiers à travers des liens symboliques pointant hors du répertoire source.

**Impact dans ce projet :** surtout chaîne d'outillage et traitement de fichiers non fiables. Aucun chemin d'exploitation via une requête web n'a été établi. L'audit des dépendances de production ne remonte aucun avis.

**Correction :** mettre à jour la dépendance transitive via son parent ou une mise à jour ciblée du verrouillage, examiner le diff puis relancer lint, tests et audit. Aucune mise à jour automatique n'a été appliquée pendant l'audit.

## Protections vérifiées et observations non classées comme vulnérabilités

### Accès, paiement et fichiers

- Les **68 routes admin autres que login/logout** référencent un garde administrateur direct. Le refus ne dépend donc pas uniquement du middleware. La solidité du garde reste affectée par S01 et S02.
- La session client est validée par `auth.getUser()` côté serveur. La simple présence d'un cookie dans le middleware n'a pas été assimilée à une preuve de connexion dans le backend examiné.
- Les commandes exposées au client sont filtrées par `customerId`. Le téléchargement d'une facture vérifie la propriété avant émission. Aucun accès croisé à une commande n'a été démontré ; scénario à deux vrais comptes non exécuté.
- Le checkout recalcule les prix à partir du catalogue, borne les quantités et le nombre de lignes, calcule les remises et la livraison côté serveur. Le prix fourni par le navigateur n'est pas utilisé comme autorité.
- Le webhook récupère la transaction auprès de Viva, compare référence, montant, devise, source et statut, puis utilise une protection d'idempotence. L'absence de signature dans le corps reçu ne permet donc pas, à elle seule, de conclure à une falsification de paiement.
- Les uploads d'images examinés exigent une session admin, contrôlent taille/type et signature binaire, emploient des noms aléatoires. Les chemins sont filtrés. La taille doit néanmoins être limitée avant `formData()` ; vidéo, PDF et concurrence n'ont pas subi de fuzzing.
- Le JSON-LD est sérialisé avec un helper d'échappement dédié ; aucun sink XSS exploitable n'a été établi dans les usages examinés. Aucune injection SQL classique ou exécution de commande via paramètres client n'a été démontrée.

### HTTP public observé

| Chemin | Statut | Observation |
|---|---:|---|
| HTTP `/` | 308 | Redirection vers HTTPS |
| HTTPS `/` | 307 | Redirection de navigation |
| `/mentions-legales` | 200 | HTML, CSP, HSTS, anti-cadrage et `nosniff` présents |
| `/admin` | 307 | Redirection sans session |
| `/api/admin/store` | 401 | Accès anonyme refusé |
| `/api/account/me` | 401 | Accès anonyme refusé |
| `/.env` | 200 | Réponse HTML, pas un fichier de variables ; aucun motif de secret ciblé détecté dans la réponse |
| `/.git/config` | 404 | Chemin non exposé lors de la sonde |

Le statut 200 de `/.env` mérite d'être remplacé par un refus/404 explicite pour les chemins réservés. **Il ne constitue pas ici une preuve de fuite de secrets.** Le script ne conserve pas le HTML reçu. Son indicateur générique `notFoundMarker` peut aussi détecter le composant d'erreur embarqué dans une page normale ; il ne suffit pas à classer une réponse en véritable 404.

### Diagnostic CSP S08 : observation, pas faille démontrée

Le middleware local transmet `x-nonce` mais pas `Content-Security-Policy` dans les en-têtes de requête destinés à Next. Le guide installé recommande les deux. Toutefois, l'analyse du HTML réellement servi sur les deux pages sondées trouve **zéro script inline exécutable sans nonce correspondant**. Il serait incorrect d'annoncer une CSP cassée ou une XSS confirmée. Aligner l'implémentation avec le guide, puis vérifier le navigateur sur les parcours complets. Le binaire déployé n'a pas été rapproché d'un commit précis.

### Défense complémentaire

Les journaux d'audit sont envoyés sans attente de persistance. Cela peut perdre des événements si une exécution serveur s'arrête ; le contexte admin renvoie aussi une identité constante, peu adaptée à plusieurs administrateurs. Préférer un envoi garanti ou `after()` et une identité réelle.

Le constructeur Supabase de service n'importe pas directement `server-only`, même si plusieurs consommateurs le font. Ajouter cette barrière au module sensible réduirait le risque d'import client accidentel. Aucune clé de service dans un bundle public n'a été démontrée.

Les cookies Supabase peuvent être accessibles au client par conception du SDK ; cela ne suffit pas à signaler une vulnérabilité. Leur usage et leurs limites sont décrits dans le [guide officiel Supabase SSR](https://supabase.com/docs/guides/auth/server-side/advanced-guide). Le cookie admin dispose bien de `HttpOnly`, `SameSite=Strict` et `Secure` en production.

## Limites et contrôles restant à effectuer

Cet audit approfondi combine code, tests locaux et sondes publiques. Il ne constitue pas un pentest exhaustif de production. Restent à vérifier :

1. **État réel Supabase** : privilèges, RLS, fonctions `SECURITY DEFINER`, triggers et migrations effectivement appliquées. Un script de vérification en lecture seule est fourni : [VERIFY-SUPABASE-PERMISSIONS-2026-09-12.sql](VERIFY-SUPABASE-PERMISSIONS-2026-09-12.sql). Il n'a pas été exécuté.
2. **Environnement de recette avec deux comptes et un admin** : accès croisés, changement de compte, reset, révocation, CSRF navigateur et modération via Data API. Les mocks locaux ne remplacent pas ces tests.
3. **Paiement de test** : rejeu, doublons concurrents, retour avant webhook, panne transitoire et reprise, stock et consommation unique des récompenses. Aucun paiement réel lancé.
4. **Infrastructure** : WAF, limites Vercel, secrets de production, MFA Supabase, configuration SMTP, sauvegardes et restauration, accès opérateurs, DNS/TLS détaillé. HTTPS a été observé, pas l'ensemble des suites TLS.
5. **Robustesse** : charge autorisée en recette, fuzzing borné des fichiers et données, tests navigateur complets, dépendances natives, contrôle des bundles et historique Git.
